# Build a production-ready, database-driven research website for Deux Voir

I want you to rebuild my existing static research website as a modern full-stack application in Replit.

## 1. IMPORTANT: EXISTING DESIGN IS THE SOURCE OF TRUTH

I have provided the existing website files:

* `index.html`
* `research.html`
* `style.css`
* individual research paper HTML files

Use these files as the **visual and content reference**.

The existing site is called **Deux Voir**.

The new application must preserve the existing visual identity and overall UI/UX as closely as possible.

Do NOT redesign it into a generic SaaS dashboard, generic AI website, Bootstrap website, Tailwind template, or modern startup landing page.

The aesthetic should remain:

* editorial
* academic
* minimal
* quiet
* sophisticated
* typography-focused
* cream / near-black
* serif-led
* lots of whitespace
* thin borders/rules
* restrained animations
* no excessive cards, gradients, shadows or rounded UI
* no unnecessary icons
* no flashy dashboard styling on the public website

The existing CSS defines the visual language. Preserve its principles rather than replacing the design with a completely different system.

The current design uses:

* Cormorant Garamond for serif typography
* Inter for UI/meta typography
* cream background
* near-black text
* muted grey typography
* thin divider lines
* approximately 760px reading width
* approximately 1100px wide overall layout
* editorial paper/research-card layout
* uppercase small metadata labels
* pill-like status badges
* understated text links

Keep this visual language.

# 2. GOAL

Convert the static website into a database-driven research publishing platform.

I should be able to manage all research papers from an authenticated admin portal.

The public website should automatically render everything from the database.

I should NOT have to manually create or edit HTML files whenever I publish a new paper.

The admin should be able to:

* create papers
* edit papers
* delete papers
* publish/unpublish papers
* change paper metadata
* write/edit the paper summary and full content using a WYSIWYG editor
* attach images inside the research content
* upload images to Cloudinary
* manage authors
* manage status
* manage venue
* manage publication/submission date
* manage keywords
* manage sections
* optionally add external links

# 3. RECOMMENDED STACK

Use a modern, maintainable full-stack framework.

Preferred:

* Next.js
* TypeScript
* PostgreSQL
* Prisma ORM

* API/server actions for mutations

Example:

Create a clean schema.

* content
* status

* authors

For keywords, use a normalized table or a clean array/string representation depending on the chosen PostgreSQL implementation.

Also support:

## PaperSection

* id
* paperId
* heading
* content
* order

However, if the WYSIWYG editor stores the entire paper body as structured rich text, avoid unnecessary duplication.

Choose the architecture that produces the cleanest CMS.

# 6. IMAGE UPLOADS

Integrate Cloudinary.

Use environment variables such as:

`CLOUDINARY_CLOUD_NAME`
`CLOUDINARY_API_KEY`
`CLOUDINARY_API_SECRET`

Never expose the Cloudinary API secret to the client.

Images should be uploaded through a secure server-side flow or signed upload mechanism.

When an image is inserted into the WYSIWYG editor:

1. User selects/uploads image.
2. Image is uploaded to Cloudinary.
3. Cloudinary returns the URL.
4. The image is inserted into the rich-text content.
5. The image remains available when the paper is rendered publicly.

Support:

* image upload
* image URL
* alt text
* optional caption
* responsive rendering

Use Cloudinary transformations where appropriate for responsive images.

Do not store image binary files in PostgreSQL.
